# Media intake storage boundary

**Recorded:** 2026-09-28  
**Status:** chosen for the P-01 server foundation

## Decision

KoeFrame owns resumable local filesystem staging for private media intake.
Upload bytes are first written to
`<staging-root>/uploads/<tenant-id>/<upload-id>.part`. After the server verifies
the complete SHA-256 digest, it links the file into
`<staging-root>/intakes/<tenant-id>/<intake-id>/<relative-path>` and removes the
temporary name. The client path is relative to that generated intake root; it
never names a Sonarr root or final library destination.

The upload table belongs to KoeFrame and is installed through its versioned
`Defdo.KoeFrame.Migrator`. Tenant identity is copied from
`Defdo.Tenant.Context` at the application boundary. The database offset is the
committed offset: retries at an older offset truncate any bytes written before
a database rollback and resend from the recorded position.

The staging service applies mode `0600` to partial files inside owner-only
`0700` directories. After checksum verification, it assigns the configured
media UID/GID to completed files with mode `0640`. KoeFrame retains ownership of
published directories and assigns the configured media group with mode `0750`;
the media process can read and traverse them without group write access.
Production sets the target media UID and GID through runtime configuration;
clients cannot request ownership or modes. The release must have permission to
assign the configured file owner/group and directory group. KoeFrame's OS user
is trusted because it owns the writable staging tree; the media group receives
read/traverse access only and must not include untrusted writer processes. The
configured storage root's ancestor directories are checked; group/world-write
is rejected even when a sticky bit is set, so an untrusted media-group process
cannot pre-create the root entry in a sticky shared directory.
KoeFrame uses `Defdo.Uploader.Adapter` from `defdo_uploader` to publish the
verified file. Its `FilesystemAdapter` is host-owned because it needs KoeFrame's
NAS root and media ownership settings.

## Ecosystem assessment

- `uses: defdo_tenant@0.17.0` — `Defdo.Tenant.Context.tenant_id/0` and
  `Defdo.Tenant.Migration.tenant_id/0` provide the tenant boundary and FK.
- `uses: defdo_migrator@0.4.1` — `Defdo.Migrator.Migration` owns version 2;
  the Ecto wrapper is generated by `mix ecto.gen.migration` and pins version 2.
- `uses: defdo_uploader@0.3.0` — KoeFrame implements its adapter contract for
  final local publication. Its `Storage.put/3` remains intended for policy-
  managed assets and S3/R2; upload sessions, chunk offsets, and NAS layout stay
  in KoeFrame.
- RustFS exposes an S3-compatible service at `s3.defdo.ninja` for separate
  object-storage integration tests. It is not the P-01 media destination,
  which must expose POSIX ownership and mode semantics to the NAS library.
- `gap: upload authentication — use defdo_auth_client` once its private Hex
  package resolves. The route requires credential introspection and a
  tenant-registered `koe_frame:media:write` scope before it can be exposed.

## Consequences

- P-01 has a server-side upload-session and local staging foundation, but the
  latest symlink and permission hardening is compile-checked only because Mix
  cannot start its TCP PubSub listener in this environment. It remains
  incomplete until database tests, the authenticated HTTP/Tus API, and Mac
  client transfer a directory tree end to end.
- Staging and final library placement are separate. Sonarr remains authoritative
  for the latter.
- The filesystem adapter requires hard-link support on the configured staging
  filesystem. Validate that on the NAS volume before operational use.
- Choose a dedicated staging root whose parent chain is not group/world writable.
  The application refuses writable ancestors, including sticky shared
  directories, so a media-group process cannot pre-create the root entry.
- This checkout could not reach the RustFS endpoint: DNS resolution for
  `s3.defdo.ninja` failed, direct access to the remembered NAS S3 port was
  refused, and no S3 test credentials were present in the process environment.
  No object was written.
- The Hub task-jobs API is not part of this intake slice. Subtitle translation
  remains blocked on the Hub contract being implemented and released.

## Authentication prerequisite

The client stores its scoped bearer credential in macOS Keychain. KoeFrame
validates it with `Defdo.AuthClient.SDK.introspect_credential/3` and establishes
the returned tenant at the request edge before invoking `Uploads`. The
application scope is `koe_frame:media:write`; it must be registered in the
IdP tenant catalog and granted only to the KoeFrame client. The upload route
does not ship while the auth package, scope, and credential are unavailable.
